## Routing algorithm

เป้าหมาย: หา **"good path"** (cost ต่ำสุด / เร็วสุด / congest น้อยสุด) จากต้นทางไปปลายทาง · มองเครือข่ายเป็นกราฟ **G = (N, E)**: N = เราเตอร์, E = ลิงก์, **c(a,b)** = cost ของลิงก์ตรง (ไม่มีลิงก์ = ∞) ผู้ดูแลกำหนด cost เองได้ เช่น 1 ทุกลิงก์ หรือแปรผกผันกับ bandwidth

## Link state: Dijkstra

ทุก node ได้ topology เหมือนกันผ่าน **link state broadcast** แล้วคำนวณ least-cost path จากตัวเองไป**ทุก node** · หลัง k รอบจะรู้คำตอบแน่นอน k ปลายทาง

<Def title="สัญลักษณ์">

**D(v)** = cost ต่ำสุดไป v เท่าที่รู้ตอนนี้ · **p(v)** = node ก่อนหน้า v บน path · **N'** = เซต node ที่รู้คำตอบแน่นอนแล้ว

</Def>

1. เริ่ม: N' = \{u\} เพื่อนบ้านของ u ได้ D(v) = c(u,v) ที่เหลือ ∞
2. หา w ∉ N' ที่ **D(w) น้อยสุด** ใส่เข้า N'
3. อัปเดตทุก v ที่ติดกับ w และ ∉ N':

$$
D(v) = \min\big(D(v),\; D(w) + c(w,v)\big)
$$

ถ้าค่าลดลง เปลี่ยน p(v) = w · ทำซ้ำจนทุก node อยู่ใน N'

<Tip>

- **เสมอกันเลือกตัวไหนก่อนก็ได้** (สไลด์เลือก y ก่อน v) cost สุดท้ายเท่ากัน
- forwarding table เก็บแค่**ลิงก์แรก** (เช่นไป w, y, z ออก (u,x) ทั้งหมด)
- ความซับซ้อน: algorithm **O(n²)** (ทำให้เหลือ O(n log n) ได้) · messages **O(n²)**

</Tip>

## Distance vector: Bellman-Ford

$$
D_x(y) = \min_v \{\, c(x,v) + D_v(y) \,\}
$$

แปล: ทางถูกสุดไป y = เลือก**เพื่อนบ้าน v** ที่ (ค่าเดินไป v + ที่ v บอกว่าไป y ได้) ถูกที่สุด · เพื่อนบ้านที่ให้ค่า min = **next hop**

<Example title="ตัวอย่างสไลด์">

u มีเพื่อนบ้าน v, x, w (cost 2, 1, 5) ซึ่งบอกว่า $D_v(z)=5,\ D_x(z)=3,\ D_w(z)=3$ หา $D_u(z)$

<Solution>

$D_u(z) = \min\{2+5,\ 1+3,\ 5+3\} = 4$ → next hop ไป z คือ **x**

</Solution>

</Example>

<Def title="คุณสมบัติ 3 อย่างของ DV">

**Iterative, asynchronous** (คำนวณใหม่เมื่อ cost ข้างตัวเปลี่ยนหรือได้ DV จากเพื่อนบ้าน) · **Distributed** (บอกเพื่อนบ้านเฉพาะตอน DV ตัวเองเปลี่ยน) · **Self-stopping** (ไม่มีใครแจ้งก็ไม่ทำอะไร)

</Def>

## LS vs DV

| ด้าน | Link State | Distance Vector |
|---|---|---|
| Message | n เราเตอร์ส่ง O(n²) | แลกแค่เพื่อนบ้าน เวลา converge ไม่แน่นอน |
| Convergence | O(n²) อาจมี oscillation | อาจมี routing loop, count-to-infinity |
| Robustness | ประกาศ **link** cost ผิด แต่ละตัวคำนวณเอง → ผิดเฉพาะวง | ประกาศ **path** cost ผิด → **black-holing** และ error แพร่ทั้งเครือข่าย |
| ข้อมูลที่รู้ | topology ทั้งหมด | แค่เพื่อนบ้าน |

## Intra-AS routing: OSPF

โลกจริงแบนไม่ได้เพราะ **scale** (ปลายทางหลายพันล้าน) และ **administrative autonomy** (แต่ละเจ้าอยากคุมเครือข่ายตัวเอง) จึงรวมเราเตอร์เป็น **Autonomous System (AS)**

- **Intra-AS:** ในเครือข่ายเดียวกัน ทุกเราเตอร์ใน AS ต้องใช้ protocol เดียวกัน (RIP, EIGRP, OSPF)
- **Inter-AS:** ระหว่าง AS ทั้งอินเทอร์เน็ตใช้ **BGP**
- **Gateway router** อยู่ขอบ AS ทำทั้ง intra และ inter · ปลายทางในอยู่ AS → intra กำหนด · ปลายทางนอก AS → ทั้งสองทำร่วมกัน

| Protocol | ประเภท | หมายเหตุ |
|---|---|---|
| RIP | DV | แลก DV ทุก 30 วิ ไม่ค่อยใช้แล้ว |
| EIGRP | DV | เคยเป็นของ Cisco เปิดปี 2013 |
| **OSPF** | **LS** | IS-IS แทบเหมือนกัน |

<Def title="OSPF (Open Shortest Path First)">

"Open" = มาตรฐานเปิด · ทุกเราเตอร์ **flood LSA** ให้ทั้ง AS **ตรงบน IP** (ไม่ผ่าน TCP/UDP) · ใช้ **Dijkstra** · ทุกข้อความถูก **authenticate**

</Def>

**Hierarchical OSPF:** AS ใหญ่แบ่ง **local area + backbone** · LSA flood แค่ใน area ตัวเอง · บทบาท: **local router** (คำนวณใน area) · **area border router** (สรุประยะไป area ตัวเองแล้วประกาศใน backbone) · **backbone router** · **boundary router** (ต่อ AS อื่น)

## Inter-AS routing: BGP

**BGP** = "กาวที่ยึดอินเทอร์เน็ตไว้" ให้ subnet ประกาศว่า "ฉันอยู่ที่นี่ ไปถึงได้ทางไหน" · **eBGP** รับ reachability จาก AS เพื่อนบ้าน · **iBGP** กระจายภายใน AS

<Figure src="ebgp-ibgp" caption="เส้นแดง = eBGP ข้าม AS · เส้นประฟ้า = iBGP ภายใน AS · gateway router (วงแดง) รันทั้งสองแบบ" width={640} />

- **path vector protocol** บน **TCP connection แบบกึ่งถาวร** (peers) ประกาศ**ทั้ง path** ไปยัง prefix (คล้าย DV แต่ส่ง path)
- message 4 ตัว: **OPEN** (เปิด TCP + authenticate) · **UPDATE** (ประกาศ/ถอน path) · **KEEPALIVE** · **NOTIFICATION** (error, ปิด)
- route = prefix + attributes: **AS-PATH** (AS ที่ผ่านมา) · **NEXT-HOP** (เราเตอร์ภายในที่เป็นทางออก)
- **import policy** ตัดสินว่าจะรับ path ไหม การประกาศ = การสัญญาว่าจะ forward ให้

<Tip title="BGP + OSPF เติม forwarding table">

**BGP บอกว่าออก gateway ไหน · OSPF บอกว่าไป gateway นั้นทาง interface ไหน**

</Tip>

<Figure src="bgp-policy" caption="Policy: B ไม่ประกาศ B-A-w ให้ C เพราะไม่ได้เงิน (C ไม่ใช่ลูกค้า B) → C ใช้ C-A-w · ลูกค้า dual-homed ไม่ประกาศ route ข้ามเพื่อไม่ให้ตัวเองเป็นทางผ่าน" width={520} />

**BGP route selection** (เสมอจึงไปข้อถัดไป): 1. local preference (policy) → 2. AS-PATH สั้นสุด → 3. NEXT-HOP ใกล้สุด (hot potato) → 4. เกณฑ์อื่น

## SDN control plane

ทำไม **logically centralized**: จัดการง่าย ลด config ผิด · คำนวณตารางที่ศูนย์กลางแล้วแจก**ง่ายกว่า** distributed algorithm · control plane เปิด → นวัตกรรม (เปรียบ mainframe → PC)

**Traffic engineering ที่ routing แบบเดิมทำยาก:** บังคับ u→z ไปทาง uvwz (ต้องปรับ link weight เท่านั้น) · แบ่ง traffic ไป 2 ทาง (ทำไม่ได้) · ให้ w ส่ง traffic 2 แบบไปคนละทาง (ทำไม่ได้ เพราะดูแค่ปลายทาง) → SDN + match+action ทำได้หมด

## ICMP และ traceroute

**ICMP** ให้ host/เราเตอร์ส่งข้อมูลระดับ network: error reporting และ echo (ping) · อยู่ **"เหนือ" IP** เพราะถูกห่อใน IP datagram · ข้อความ = **type + code** + 8 bytes แรกของ datagram ที่ทำให้เกิด error

| Type/Code | ความหมาย |
|---|---|
| **0/0** | echo reply (ping) |
| 3/0, 3/1, 3/2 | network / host / protocol unreachable |
| **3/3** | **port unreachable** |
| **8/0** | echo request (ping) |
| **11/0** | **TTL expired** |
| 12/0 | bad IP header |

## Network management

monitor / configure / control เครือข่ายด้วย hardware + software + คน · องค์ประกอบ: **managing server** (มีคนในวงจร) · **managed device** มี **agent** · **data** (config, operational, statistics) · **management protocol**

วิธีของ operator: **CLI** (ทีละเครื่องผ่าน ssh) · **SNMP/MIB** (query/set ข้อมูลใน MIB) · **NETCONF/YANG** (มองทั้งเครือข่าย config หลายเครื่องพร้อมกัน)

- **SNMP** 2 โหมด: request/response และ **trap** (agent แจ้งเองเมื่อผิดปกติ) · Get/GetNext/GetBulk/Set = manager → agent · Response, Trap = agent → manager
- **MIB** = ข้อมูลในอุปกรณ์ นิยามด้วยภาษา **SMI** (เช่น UDP MIB: UDPInDatagrams, UDPNoPorts …)
- **NETCONF** = RPC + **XML** บน transport ปลอดภัย (**TLS**) · **atomic commit** ข้ามหลายอุปกรณ์ · operation: get-config, get, edit-config, lock/unlock, create-subscription
- **YANG** = data modeling language ที่ NETCONF ใช้ กำหนด structure / constraint ของ config

| | SNMP world | NETCONF world |
|---|---|---|
| Protocol | SNMP | NETCONF (RPC + XML บน TLS) |
| ภาษานิยามข้อมูล | SMI | YANG |
| เน้น | query/set ทีละเครื่อง, monitor | config หลายเครื่องแบบ atomic |

## สรุป + ควิซ

| เรื่อง | จำ |
|---|---|
| Dijkstra | เลือก D น้อยสุด → อัปเดต $D(v)=\min(D(v), D(w)+c(w,v))$ · O(n²) |
| Bellman-Ford | $D_x(y)=\min_v\{c(x,v)+D_v(y)\}$ · min มาจาก next hop |
| DV | iterative/async, distributed, self-stopping · bad news ช้า |
| OSPF | LS, flood LSA บน IP, authenticate, hierarchical |
| BGP | path vector บน TCP · eBGP/iBGP · AS-PATH, NEXT-HOP · hot potato |
| SDN | northbound = app, southbound = switch (OpenFlow) |
| traceroute | UDP TTL 1,2,3… ได้ 11/0 จนได้ 3/3 |

<Example title="ข้อ 1">

กราฟหลัก source = u ถ้าเปลี่ยน c(x,y) จาก 1 เป็น 3 เส้นทางไป z เปลี่ยนไหม?

<Solution>

D(y) ผ่าน x = 1+3 = 4 ผ่าน w: D(w) ผ่าน x = 4, ผ่าน v = 5 → D(w) = 4 → y ผ่าน w = 4+1 = 5 → D(y) = 4 (ผ่าน x) · z: ผ่าน y = 4+2 = 6, ผ่าน w = 4+5 = 9 → **z = 6 ทาง u→x→y→z** เส้นทางเดิมแต่ cost เพิ่มจาก 4 เป็น 6 (ลองในเครื่องมือ Dijkstra โดยกด cost ของลิงก์ x–y)

</Solution>

</Example>

</Solution>
